# Пилотирование новых ролей (role-trials)

Формат отслеживания гипотез о пользе новой роли — заимствован по образцу `lpf-hypothesis-log.md` из MIM-exocortex (см. `claude/comparison-mim-vs-lpf.md` в Project), адаптирован под LPF. Новая роль не внедряется сразу насовсем — сначала пилот с явным критерием успеха/провала и датой сверки, вердикт выносится на DRR (трек «Роли», регламент [часть 9](../docs/reglament/09-pravila-drr.md)).

Это же место закрывает вопрос «как знакомиться с новыми агентами и оценивать их полезность» — вместо отдельной роли-менеджера (R31 в MIM, см. ниже «Отклонённые роли») эту функцию выполняет сам цикл: Candidate-роль → пилот здесь → вердикт на DRR → adopt / drop / improve.

## Активные пилоты

### Верификатор (заимствовано из R23 MIM-exocortex)

- **Гипотеза:** независимая проверка вывода/артефакта в изолированном контексте (суб-агент, не тот же чат) ловит ошибки, которые пропускает проверка «тем же контекстом, который и делал вывод» — потому что тот контекст уже верит в свою правоту.
- **Механизм:** sub-agent. Для проверки конкретного артефакта (текста, вывода, решения) запускается отдельный агент, получающий ТОЛЬКО артефакт + критерии проверки — без истории рассуждений, которые к артефакту привели.
- **Когда применять:** для значимых решений/выводов с высокой ценой ошибки (архитектурные решения по IWE, тексты для внешней аудитории, серьёзные развилки) — не для рутины, иначе это просто лишний шаг.
- **Активация (уточнено 05.09.2026):** у Марии нет инструмента запуска суб-агента (чат-режим, Claude.ai Projects) — практический протокол ручной. Агент любой ветки, заметив решение под критерием выше, формирует пакет «артефакт + критерии проверки» и предлагает Марии вставить его в новый чат без истории; вердикт из того чата Мария приносит обратно. Подключено в README (пункт 9, применимо к любой ветке) и в `prompts/project-branch-prompt.md` (указатель на README).
- **Критерий успеха:** за период пилота хотя бы один раз находит реальную проблему, которую сама Мария или основной контекст не заметили.
- **Критерий провала:** не находит ничего за 3-4 попытки, ИЛИ создаёт лишний шаг без пользы (шум, а не сигнал).
- **Дата первой сверки:** через 3-4 использования или через 4 недели (14.09–03.10.2026) — что раньше.
- **Статус:** Пилот, начат 05.09.2026.

### Экстрактор (заимствовано из R2 MIM-exocortex)

- **Гипотеза:** явный роутинг-тест «это знание домена (переживёт текущий проект) или контекст конкретной задачи (устареет вместе с ней)?» предотвращает смешение будущего Pack с оперативными `context.md` проектов.
- **Механизм:** правило-инструкция (не отдельный агент-сценарий) — при появлении нового факта/находки в проектном чате агент прогоняет тест выше: домен → Pack, операционка → `context.md`/DS-документ. Домены Pack не заводятся заранее списком — если факт признан Pack-достойным, а `pack/<домен>.md` для этого домена ещё не существует, файл создаётся в этот же момент (по шаблону `pack/_template.md`).
- **Когда применять (решение Марии 05.09.2026): базово, в любом проектном чате** — не только под активированным Аналитиком, как предполагалось изначально.
- **Активация (уточнено 05.09.2026):** подключено напрямую в `prompts/project-branch-prompt.md` (раздел «РОУТИНГ В PACK», работает с момента старта сессии любого проектного чата) и продублировано в README (раздел «Проектные чаты»). Для проектных чатов, созданных до 05.09.2026 (Custom Instructions уже вставлены как статический текст), Мария переносит правку вручную — README и repo-map не покрывают уже вставленный текст Custom Instructions, это не живая ссылка на репозиторий.
- **Критерий успеха:** за период пилота Pack не начинает дублировать `context.md` и наоборот.
- **Критерий провала:** путаница/дублирование несмотря на роутинг, ИЛИ роутинг тратит больше времени на классификацию, чем экономит.
- **Дата первой сверки:** при создании первого доменного файла Pack + через 2-3 находки после этого.
- **Статус:** Пилот, начат 05.09.2026 (шаблон готов, доменные файлы появятся по мере надобности).

### Коуч (новая роль, придумана по запросу Марии 05.09.2026 — не заимствована из MIM)

- **Гипотеза:** активное отслеживание в формате трекера (стрик по обязательным ритуалам + обязательный пересмотр каждой активной привычки раз в 3 недели + накопительный анализ) даёт дисциплину и видимость прогресса, которых не даёт пассивное Telegram-напоминание (`automation/reminders-routine.md`) — напоминание не показывает историю и не вынуждает принять явное решение по привычке.
- **Механизм:** третья роль в уже существующей ветке (Claude Project) «Хаб+Дневник» — не отдельный Project (исправлено 05.09.2026, по прямому указанию Марии; первоначальный вариант с отдельным Project отменён в тот же день, до создания). Читает уже существующую телеметрию (не собирает новую сама) и ведёт `telemetry/coach-progress-2026-09.md`. Два слоя: обязательные ритуалы (постоянный стрик, без пересмотра) и активные привычки (набор меняется; у каждой — дата старта и обязательный пересмотр через 21 день, вердикт закреплена/продолжаем/меняем). Вечерняя фиксация — часть закрытия дня, в том же чате, следом за вечерним чекином Дневника, не вместо него. Эмоционально значимые находки у Коуча не остаются — уходят мостом в `telemetry/signals-inbox-2026-09.md` (без Gate, как сырой сигнал) и интерпретируются Дневником — тот же принцип, что и в `automation/session-close-routing.md`; Коуч не дублирует Дневник.
- **Когда применять:** вечером, как часть закрытия дня, в этом же чате; в течение дня — по запросу, для быстрой сверки стрика.
- **Активация (уточнено 05.09.2026):** без создания нового Project. Custom Instructions ветки «Хаб+Дневник» уже существуют и статичны (как и у проектных чатов) — поэтому один раз вручную дополняются коротким указателем на `prompts/coach-prompt.md` (патч-фрагмент — см. README, раздел «Коуч»). После этого разового патча роль работает в том же чате постоянно.
- **Критерий успеха:** к первому пересмотру (26.09.2026) хотя бы одна активная привычка держит трекер регулярно заполненным, и хотя бы один «провал» зафиксирован честно, без пропуска записи (значит, трекер используется, а не саботируется).
- **Критерий провала:** трекер становится источником вины/давления без изменения поведения, ИЛИ не заполняется больше недели подряд.
- **Дата первой сверки:** 26.09.2026 — пересмотр привычек «Слот обучения» и «Тренировка», тем же поводом сверяется и сама роль «Коуч».
- **Статус:** Пилот, начат 05.09.2026. Трекер: `telemetry/coach-progress-2026-09.md`.

## Отклонённые роли (05.09.2026) — не пересматривать без новых оснований

- **Менеджер оргразвития (R31 MIM)** — не заводится отдельной ролью. Функция «знакомство с новым агентом/оценка пользы» закрыта самим этим файлом + циклом DRR §16 (три трека), отдельный агент поверх процедуры был бы дублированием.
- **Аудитор (R24 MIM)** — дублирует существующую «Процедуру проверки целостности системы» (`automation/agent-workflow-rules.md`). Заводить роль поверх нет смысла, пока не появится сигнал, что ad hoc-варианта не хватает.
- **Артефактор (R29 MIM)** — в MIM это часть кодовой WP-дисциплины сборки артефактов; в LPF нет аналогичного конвейера, применить не к чему.
- **ArchGate-метод (MIM)** — не роль, а приём (формальное сравнение альтернатив). Берётся не сюда, а как метод внутри Аналитика — см. добавление FPF-паттернов (Lawful Comparison, Decision Theory) в `prompts/analyst-prompt.md`.

## Цикл пересмотра

Пилоты пересматриваются на каждом DRR (трек «Роли»). Вердикт по каждому пилоту на дату сверки — один из: **adopt** (снять статус «пилот», роль постоянная), **drop** (гипотеза не подтвердилась, роль закрывается), **improve** (гипотеза частично верна, механизм требует правки — новый пилот с уточнённым критерием).

**Дополнительная линза (добавлено 05.09.2026, по итогам семинара Aisystant «Интеллектуальная рабочая среда», `obuchenie/2026-06-07-aisystant-seminar-iwe.md`):** при вынесении вердикта, помимо критериев успеха/провала конкретного пилота, спросить общий вопрос — эта роль усиливает собственное мышление/навык Марии (экзоскелет), или подменяет его и отучает справляться без инструмента (протез)? Тот же вопрос — шаг «Экзоскелет-проверка» в `prompts/dnevnik-prompt.md`, раздел STRATEGIZING; здесь он прицельно применяется к активным пилотам ролей на дату их сверки.
