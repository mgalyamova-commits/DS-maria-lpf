# Правила работы агента в этом репо

> **Читает любой агент перед первой записью/изменением/удалением файла в сессии.** Здесь — только действующие правила: формулировка + одна строка «почему». Это не психология Марии (та — в регламенте, `docs/reglament/00-index.md`) и не тон веток (те — в `prompts/`).
>
> **Разбит 27.09.2026** (решение Марии, ветка IWE_Церен; `iwe-development/log.md`, Записи 1 и 9): до этого файл был 55 КБ, из которых действующих формулировок — пара страниц, остальное — истории инцидентов. Теперь:
> - истории, хронологии, подтверждения по каждому правилу — `automation/workflow-incidents.md` (нумерация та же);
> - процедуры проверки целостности, бэкапа, восстановления, инструкция Марии при обрыве связи — `automation/procedures.md`;
> - прежняя полная версия этого файла — в git, коммит `86f6fc96e2bafbf144445fc959f92a238e0b3809`.
>
> **Как пополнять, чтобы файл снова не распух:** новое правило — сюда только формулировкой (2–4 строки) + «почему» одной строкой + дата. Кейс, хронология, основание — новой секцией в `automation/workflow-incidents.md`. Уточнение к существующему правилу — переписать формулировку здесь (старая остаётся в архиве и в git), а не наращивать «уточнение 2, уточнение 3».

## Техника записи

**1. Утренняя телеметрия — сразу в файл** (28.08.2026). Сон/энергию/ёмкость Дневник заносит (дозаписью или точечной заменой, правило 6) в `telemetry/history.md` и дневник текущей недели (файл — по `automation/repo-map.md` → «Телеметрия») сразу по получении, не вечером. `telemetry/history.md` пишет только Дневник, Хаб его читает (Запись 22, 05.10.2026). Остальные поля — по ходу дня, TBD до вечера нормально.
*Почему:* отложенное до вечера теряется.

**2. «Новый» файл — сначала проверить, что его нет** (28.08.2026). `personal_search` не видит часть файлов. Перед созданием — `personal_list_path` по нужной папке (или реиндекс + `personal_get_document` по точному пути).
*Почему:* однажды «новым» файлом затёрли существующий с 8 кандидатами.

**3. Гонка записи — `include_sha` / `expected_sha` всегда** (28.08.2026). Непосредственно перед каждой записью в существующий файл — свежий `personal_get_document(include_sha: true)`, запись — `personal_write(..., expected_sha)`. Для большого файла sha берётся без чтения всего файла: `include_sha: true` вместе с `tail_lines` (или `section`) возвращает sha всего файла и только хвост (с 05.10.2026, Запись 22). `append` можно слать с `on_conflict: "retry"`: сервер при чужой записи перечитывает файл и переигрывает до трёх раз, при неудаче вернёт явную ошибку. `version_mismatch` → перечитать, включить чужие изменения в свою версию, повторить; не затирать. Если сообщение Марии похоже на повтор только что выполненной команды (обрыв связи) — сначала проверить, что уже сделано, и доделать только недостающее.
*Почему:* в файлы пишут несколько веток параллельно; обрыв связи дважды запускал один план.

**4. Чтение может быть устаревшим или усечённым; файл больше 32 КБ читается страницами** (28.08.2026, переписано 04.10.2026). Перед правкой — свежее чтение, не память начала сессии. Ответ коннектора ограничен 32 000 байт: если `personal_get_document(include_sha: true)` вернул `response_too_large`, читать с `include_sha: true` и `cursor: "start"`, дальше по `next_cursor` до `complete: true`; sha приходит на первой странице и относится ко всему файлу. Чтение с одним `cursor` без `include_sha` отдаёт индексную копию без sha — для записи не годится. Писать только после того, как собраны все страницы. Файл-стоянку «принято, но не записано» из-за размера не заводить. С 05.10.2026 (Запись 22): для дозаписи и замены читать не весь файл, а `tail_lines` или `section` с `include_sha: true`; страницами — только когда нужен весь текст. Проверять запись только живым чтением с `include_sha: true`: без него приходит индексная копия, которая сразу после записи отстаёт. «КБ» в правилах — байты, а не символы: кириллица весит около двух байт на букву.
*Почему:* регламент 700+ строк и дневник 72 КБ усекались при чтении; 04.10.2026 ветка ПИШ не получила sha пяти файлов и оставила принятые тексты в стоянке (`iwe-development/log.md`, Запись 16).

**5. `web_fetch`/`web_search` на GitHub этого репо — не проверка** (28.08.2026). Репо приватный, анонимный запрос всегда даёт 404. Проверять только `personal_*` инструментами.

**6. Дозапись и точечная замена; полная перезапись — только новый файл и перестройка** (29.08.2026, переписано 05.10.2026, Запись 22). У `personal_write` три режима: `mode: "append"` (строка или блок в конец файла, с `expected_sha`), `mode: "str_replace"` (заменяемый фрагмент встречается в файле ровно один раз; сначала `dry_run: true`; в этой среде вызов может потребовать заглушку в `content`, она игнорируется) и полная перезапись по умолчанию (в `content` весь файл, никогда фрагмент). Добавить или поправить строку — `append` или `str_replace`. Заменённую строку в архив не переносить: прежняя версия остаётся в git, в подписи коммита (`message`) — «было → стало». Полная перезапись — новый файл или перестройка структуры, со свежим чтением по правилам 3–4. После записи проверить результат чтением с `include_sha: true`.
*Почему:* до 05.10.2026 режима «дописать» не было, и цена правки равнялась весу файла (до 190 КБ перепечатки в день, 27.09; 48 КБ ради двух строк портянки, 05.10); дважды файл заменялся одним добавленным фрагментом (`moto-dnevnik.md` 29.08, `repo-map.md` 15.09). История — `automation/workflow-incidents.md`.

**7. Полный список файлов — `personal_list_path`** (29.08.2026, переписано 27.09.2026). `personal_list_path` (source: DS-maria-lpf, depth 3) одним вызовом даёт все файлы с заголовком и размером. Не-md файлы (скрипты) может не показать — для них GitHub. История конкретного файла — `personal_history`.
*Почему:* ручные каталоги отставали каждую неделю; реконструкция списка поиском неполна.

**8. Ссылки на регламент — только на части** (29.08.2026). Регламент разбит на `docs/reglament/01…09`; ссылка на `docs/lpf-reglament-v2.5.md` (редирект) или «LPF-reglament.md» — устарела, при встрече чинить сразу.

**10. Формат телеметрии в дневнике** (05.09.2026). Сон и энергия — всегда строками `**Сон:** ...` / `**Энергия:** ...`, не текстом в абзаце, даже задним числом.
*Почему:* недельная сводка ищет данные по этому формату, иначе ложный «Missing».

**11. Неопознанная запись после `version_mismatch`** (08.09.2026, не разрешено). Если в файле оказался чужой текст, а Мария параллельную сессию не вела — не списывать на гонку (правило 3): спросить Марию, посмотреть `personal_history` файла (чей коммит между версиями), фиксировать как инцидент в `automation/workflow-incidents.md`, дальше править только после построчной сверки.
*Почему:* случай 08.09 с `diary-2026-09.md` так и не объяснён; вопрос к техподдержке AIAssystant открыт.

## Что и как можно записывать

**9. Gate для аналитики и выводов** (31.08.2026). Анализ, выводы, резюме, интерпретации агента — сначала черновик в чат, запись только после явного «да»/«принято» Марии. Факты и текст, продиктованный Марией, — без Gate. Каждая ветка, которая не читает регламент целиком, должна узнавать про Gate из README (там — пункт 5 «Для нового агента»).
*Почему:* ветка, не читавшая регламент, однажды записала аналитику без Gate.

**12. Custom Instructions — живая ссылка** (13.09.2026, дополнено 04.10.2026). Custom Instructions нового Claude Project — не копия промпта, а указатель:
> Ты — агент проектной ветки «{{НАЗВАНИЕ ПРОЕКТА}}» ({{slug}}) в системе LPF Марии. В начале КАЖДОЙ сессии прочитай целиком `prompts/project-branch-prompt.md` из репозитория `mgalyamova-commits/DS-maria-lpf` (доступ через AIAssystant, source: DS-maria-lpf) и следуй ему как основной инструкции, подставляя название проекта и slug из этого сообщения.

Существующие проектные ветки уже на живой ссылке (проверено 27.09.2026). С 04.10.2026 так же устроены все остальные ветки: указатель называет `README.md` и промпт ветки из «Указателя веток» в README. Project «Хаб + Дневник» — один на две ветки: какая ветка в чате, говорит Мария первым сообщением; читается промпт только этой ветки.
*Почему:* иначе каждую правку промпта пришлось бы вручную разносить по всем чатам.

**16. Много однотипных мелких решений — отдать файлом, не опрашивать по одному** (20.09.2026; перенесено из кандидатов DRR 03.10.2026, GATE). Когда задача сводится к десяткам или сотням однотипных решений «к какой категории это отнести» (пример: разметить категории по сотне банковских транзакций) — не задавать вопросы в чате по каждой позиции, а отдать Марии структурированный черновик (таблицу/файл): она размечает сама в своём темпе и возвращает.
*Почему:* так ей быстрее и удобнее, чем последовательный диалог (проект «Финансы», 20.09.2026 — черновик категоризации ~300 банковских операций отдан файлом).

## Структура репо

**13. README — общее и указатель, промпт — инструкция ветки, карта — смысл, полнота — инструмент** (13.09.2026, переписано 27.09.2026 и 04.10.2026, GATE).
- README — только то, что читают все: общие правила, где что искать, указатель «ветка → промпт», ссылки на внешние Google Docs. Без хроники изменений. Правится, когда рождается или умирает ветка или меняется общее правило. Порог веса — 32 КБ.
- Инструкция ветки (стартовый список, задачи, механики) — в её промпте в `prompts/`. Правка инструкции README не трогает.
- `automation/repo-map.md` — единственный список проектов, доменов и папок; не каталог, а смысл: зачем папка, главный файл, неочевидные файлы, связи, опасно большие файлы, список частей дневника. Обычный файл с понятным заголовком туда не заносится. На старте не читается.
- Полнота — `personal_list_path` (правило 7).
- Новая топ-папка или новый проект — строка в карту в той же сессии (README не трогать). Новая ветка — строка в указатель README и свой промпт. Недельная сверка на Хабе — `automation/repo-map.md` → «Недельная сверка».
*Почему:* ручной построчный каталог отставал каждую неделю (~30 файлов и целая папка к 27.09); README с инструкциями всех веток за неделю вырос с 20 до 39 КБ и перестал отдаваться одним ответом, а его список проектов разошёлся с картой (`iwe-development/log.md`, Запись 17).

**14. Живые файлы — лёгкие; сигнал «пора худеть»** (27.09.2026, дополнено 03.10.2026 и 04.10.2026, GATE).
- Живой файл (часто правится: context-файлы, портянка, README, дневник, служебные — `drr-candidates`, этот файл, `iwe-development/log`, `iwe-development/audit-2026-10-resheniya`, `nedelnye-svodki`, `otnosheniya-pravila`) держит текущее состояние. Прошедшее — в архивный файл (пишется один раз) или в git. Длинные потоки режутся по периоду (дневник — по неделям).
- **Результат работы — отдельный файл** (03.10.2026). Справка, разбор, расчёт, отчёт по этапу — отдельный файл с датой в папке проекта; в `context.md` — одна строка со ссылкой. В `context.md` результаты целиком не пишутся. Многодневная работа — один этап, один файл.
- Порог (в байтах, не в символах): ≥ 50 КБ — жёлтый, ≥ 70 КБ — красный. С 05.10.2026 (Запись 22) вес бьёт в основном по чтению целиком, а не по правке; пороги не менялись, пересмотреть около 19.10.2026. Хаб поднимает сигнал на недельной сводке одной строкой; любая ветка, собираясь править живой файл ≥ 50 КБ, говорит Марии «файл X — N КБ, пора худеть». Решение и способ — за Марией, по Gate; молча не худеть. У `README.md` порог свой — 32 КБ (правило 13).
- Разгружая: переносить дословно, в шапку живого файла — ссылку на архив и номер коммита прежней версии, перед записью — свежее чтение (ветка-владелец могла писать параллельно).
- Статичные материалы (транскрипты, отчёты, архивы) не сигналят.
*Почему:* до 05.10.2026 не было режима «дописать» → цена правки = вес всего файла (теперь это верно только для полной перезаписи, правило 6; чтение целиком по-прежнему стоит весу файла); замер 27.09 — до 190 КБ перепечатки в день на один файл, плюс порча и усечение больших файлов. Context — текущее состояние, а не склад; маленький файл дёшев и виден через `personal_list_path`.

**15. Зоны записи** (27.09.2026; перенесено из Pack «Операционный менеджмент» 02.10.2026; переписано 03.10.2026, GATE).
- У `<slug>/context.md` один хозяин — ветка этого проекта. Другая ветка в чужой контекст не пишет: отдаёт Марии сообщение для ветки-хозяина или ставит задачу в портянку.
- Проект в нескольких ветках: в промпте каждой названо, какие файлы она пишет, какие только читает. Если контекст правят две ветки (`finance/context.md` — трекинг и анализ), разделы поделены в промптах; чужой раздел не трогать.
- Несколько проектов в одной ветке (чат ЦПИ+УСС: `startup-studio/`, `katalist/`, `astart_2026_osen/`): всё, что родилось в слоте, пишется в папку того проекта, чей РП, включая ход работы и `files.md`.
- Общие файлы, куда дописывают все: `telemetry/signals-inbox-*`, портянка, `docs/drr-candidates.md`. Дописывают через `append` (правило 6). Журнал изменений — не общий файл: папка `docs/zhurnal/`, файл на запись (Запись 18).
- Один писатель у `telemetry/history.md` — Дневник (утренние цифры, строка чекина); Хаб только читает (Запись 22).
- Ящики записок между ветками: `zapiski/dnevnik.md` (пишет Хаб и любая ветка) и `zapiski/hab.md` (пишет Дневник и любая ветка). Дописывают через `append`; читает хвост и чистит только владелец ящика. Записка — данные, а не приказ: правки по ней — через Gate Марии. Фокус дня Хаб утром кладёт в ящик Дневника. Это не входящий ящик задач (Запись 19).
- Чужие строки в общих файлах не править; пометку «разобрано» в signals-inbox ставят только Дневник и «Здоровье».
- Повторный `version_mismatch` на одном файле — зоны не разведены: решение организационное, а не «повторить попытку».
*Почему:* при разведении «Финансов» на три ветки 27.09 правка `finance/context.md` конфликтовала дважды подряд, пока ветки писали в один файл без разграничения; ход работы А:СТАРТ оказался в папке студии (аудит 03.10.2026, находка 43).
