# Правила работы агента в этом репо

Операционные правила для любого агента (Claude, Hermes, Claude Code) — как вести файлы, а не про психологию пользователя (это в `docs/reglament/00-index.md`, LPF-регламент). Новое правило добавляется отдельным пунктом с датой, без вычитки и переформулировки старых при каждом добавлении.

**Любой агент, который создаёт, перезаписывает или удаляет файлы в этом репозитории, обязан прочитать этот файл перед первой такой операцией в сессии.** Если в ходе работы обнаружен новый системный риск/баг инструментов — фиксировать сюда отдельным пунктом с датой. `docs/drr-candidates.md` — не то место: он про паттерны Марии из дневника, не про инструменты и файловые операции.

## 1. Утренняя телеметрия — сразу в файл (с 28.08.2026)

Утренние метрики (сон/энергия/ёмкость) агент-Дневник заносит в `telemetry/history.md` и `telemetry/diary-2026-08.md` сразу по получении от пользователя в чате, не дожидаясь вечера. Остальные поля (обед/ужин/тренировка/алкоголь/триггеры/эмоциональный фон) дозаполняются по ходу дня или на вечернем чекине — значение TBD в них до вечера нормально, это не ошибка агента.

## 2. Перед созданием «нового» файла — проверять через reindex, не только search (с 28.08.2026)

`personal_search` систематически не находит существующие файлы репо из-за отставания индекса (наблюдалось дважды за 28.08: `automation/repo-map.md` и `docs/drr-candidates.md` — оба уже существовали, но не находились поиском). Перед тем как писать файл по новому пути и считать его новым — сначала явно запустить `personal_reindex_source`, дождаться `succeeded`, и только потом `personal_get_document` по точному пути. Если результат «Document not found» уже после свежего реиндекса — файла действительно нет, можно создавать. Нарушение этого порядка привело к перезаписи и временной потере 8 исторических кандидатов в `docs/drr-candidates.md` (восстановлены тем же днём).

## 3. Риск гонки записи между параллельными ветками (с 28.08.2026)

Несколько веток/чатов могут писать в один и тот же файл репозитория через `personal_write` (полная перезапись) в течение одной и той же сессии-дня. Наблюдение 28.08: файл `docs/drr-candidates.md` был закрыт с 10 пунктами в одной ветке, а при следующей проверке (после форс-реиндекса) в нём уже было 12 — раздел добавлен другой веткой параллельно. Правило: для общих файлов (портянка, кандидаты, регламент, дневник) перед любой записью — свежий реиндекс + чтение непосредственно перед `personal_write`, а не опора на контекст, прочитанный в начале сессии. Если после этого обнаружены чужие изменения — включить их в свою запись, а не затереть.

**Дополнение (30.08.2026): у `personal_write` есть параметр `expected_sha`, снижающий этот риск технически.** Обнаружено на практике: при записи `docs/portyanka-obshiy-stek.md` без `expected_sha` инструмент вернул предупреждение — «Файл существовал, а expected_sha не передан — параллельные правки могли быть молча перезаписаны. Перед правкой существующего файла читай get_document(include_sha: true) и передавай его sha в expected_sha». Практическое следствие: для существующих общих файлов — читать через `personal_get_document(..., include_sha: true)` непосредственно перед записью и передавать полученный `sha` в `expected_sha` при вызове `personal_write`. Это не отменяет практику «свежий реиндекс + чтение перед записью» (см. основной пункт 3 выше), а добавляет техническую страховку поверх неё — если sha разошёлся, `personal_write` должен вернуть ошибку/конфликт вместо молчаливой перезаписи чужих правок.

**Подтверждено Марией 30.08.2026** — оставлено как есть (не понижать в кандидата), несмотря на то что было добавлено в момент, когда параллельно шла отдельная дискуссия об этом же риске в ветке «Обучение».

**Подтверждение работы на практике (31.08.2026):** метод сработал именно как описано — `personal_get_document(filename=..., include_sha=true)` вернул `sha` явным полем в структурированном ответе (не в тексте содержимого, а отдельно в объекте результата). Переданный в `personal_write(..., expected_sha=...)` этот `sha` прошёл без предупреждения — запись выполнена, новый `sha` вернулся в ответе. До этого момента `include_sha`/`expected_sha` не использовались за отсутствием ясности, как именно их вызывать; теперь подтверждено — вызывать оба параметра явно при каждой правке существующего файла, а не полагаться на вызов без них.

## 4. `personal_get_document` может возвращать устаревший/неполный контент вне контекста поиска (с 28.08.2026)

Отдельно от риска #2 (индекс поиска): сам `personal_get_document` по точному пути иногда отдаёт кэшированный или частичный снимок файла (например, только первый раздел большого документа), даже без предшествующей записи в этой сессии. Наблюдалось дважды за 28.08 при проверке `docs/drr-candidates.md`. Единственный надёжный способ подтвердить актуальность содержимого файла, который мог измениться (см. риск #3) — форс-реиндекс (`personal_reindex_source` → дождаться `succeeded`) и затем `personal_search`/`personal_get_document`. Для файлов, которые правит только текущая сессия и по которым только что был `personal_write`, риск ниже, но не нулевой — при малейшем сомнении перепроверять тем же способом.

**Уточнение (29.08.2026): `README.md` — файл с наибольшей наблюдаемой частотой этого бага.** За одну сессию 28-29.08 зафиксировано 4 случая, когда `personal_get_document` по `README.md` возвращал версию без правок, сделанных этой же сессией минуты назад. Вероятная причина — README редактируется чаще других файлов (любое новое правило/файл/ссылка проходит через него, см. правило #6 в разделе «Кандидаты»), поэтому кэш успевает разойтись с реальным содержимым чаще. Практическое следствие: если `README.md` уже редактировался в этой сессии, перед следующим чтением или правкой — обязательный форс-реиндекс, без исключений «наверное, ещё актуально».

**Уточнение 2 (29.08.2026): усечение не всегда про устаревание — иногда про размер.** На больших файлах (пример: неразбитый `docs/lpf-reglament-v2.5.md` до 700+ строк, а также этот файл `agent-workflow-rules.md`) `personal_get_document` возвращает только часть документа (то первый раздел, то последний, то произвольный кусок из середины), даже сразу после форс-реиндекса и без признаков гонки записи. Похоже, инструмент отдаёт один чанк поискового индекса, а не файл целиком, и большие файлы просто не помещаются в один чанк. Файлы сопоставимого объёма с `docs/otnosheniya-pravila.md` (в несколько раз меньше) такого не показывали. **Практическое следствие подтверждено на практике 29.08.2026:** `docs/lpf-reglament-v2.5.md` разбит на 9 частей + оглавление в `docs/reglament/` — см. новую структуру. Старый путь оставлен редиректом.

**Уточнение 3 (30.08.2026): собственное наблюдение агента «Обучение».** Файл `automation/agent-workflow-rules.md` был прочитан один раз при онбординге сессии (~07:49 НСК) и не перечитывался ~12 часов, вплоть до следующего явного чтения с `include_sha` перед записью (~20:20 НСК). За это время в файле независимо появилось «Дополнение (30.08.2026)» к правилу 3 (про `expected_sha`) — агент не видел его до фактического перечтения, хотя формально «читал этот файл в начале сессии». Нельзя достоверно отличить два объяснения: (а) кэш действительно был устаревшим, (б) файл был на самом деле изменён другой веткой в этот промежуток, а не было настоящей стейл-выдачи. Практическое следствие то же: файл, прочитанный в начале длинной сессии, нельзя считать актуальным к моменту записи спустя часы — нужен свежий `personal_get_document` непосредственно перед любой правкой, независимо от того, сколько времени прошло.

## 5. Анонимный `web_fetch` на GitHub не подтверждает существование/содержимое файла в этом репозитории (с 28.08.2026)

Репозиторий `DS-maria-lpf` приватный. Анонимный (без авторизации) `web_fetch` на `github.com/mgalyamova-commits/DS-maria-lpf/...` вернёт 404 независимо от того, существует файл или нет — это ошибка доступа, не подтверждение отсутствия. Наблюдалось 28.08: `web_fetch` дал 404 на файл, который на тот момент существовал. Никогда не использовать `web_fetch`/`web_search` на GitHub-адреса этого репозитория как способ проверки — только `personal_*` инструменты (`personal_get_document`, `personal_search`, с учётом рисков #2 и #4 выше).

## 6. Собственная ошибка агента: частичная перезапись вместо полной (с 29.08.2026)

Отдельно от рисков стейл-рида инструментов (#3, #4) — прямое нарушение агентом собственного известного правила «читать целиком → переписывать целиком». Наблюдалось 29.08: агент-Дневник вызвал `personal_write` по `docs/moto-dnevnik.md`, передав в `content` только новый фрагмент (одну добавляемую секцию) без предварительного свежего чтения всего файла — файл был полностью заменён этим фрагментом, весь остальной контент (несколько разделов, накопленных в этой же сессии) временно потерян. Обнаружено сразу при проверке через форс-реиндекс, восстановлено из последней полной версии, видимой в контексте сессии.

**Правило:** независимо от того, добавляется ли контент («допиши абзац») или переписывается целиком — перед КАЖДЫМ `personal_write` в существующий файл обязательны: (1) свежий `personal_get_document` (при сомнении — с предварительным форс-реиндексом, см. #4), (2) сборка полного нового содержимого файла (старое + новое) в `content`, а не только нового фрагмента. Это применимо даже когда правка кажется маленькой и «явно безопасной» — именно на таких мелких правках риск пропустить полный цикл выше всего.

## 7. Репозиторий значительно шире, чем знает README (с 29.08.2026)

Обнаружено при попытке полного бэкапа 29.08: реиндекс показал 31 файл, а README на тот момент документировал только ~19. Недостающий слой — 9 проектных папок в корне (`<slug>/context.md`: helsnet, helsko, motoferma, himozin, gpb-mbs, tandem, openbio, zhivye-sistemy, fondobrazovanie), `startup-studio/` (2 файла), `automation/reminders-routine.md` (конфигурация Telegram-напоминаний). README ошибочно утверждал, что контекст проектов живёт только в Google Docs. `automation/repo-map.md` оказался более актуальным (частично знал про проектные папки), но тоже не полностью синхронизирован с README. Исправлено в README 29.08.2026.

**Правило:** нет отдельного инструмента «показать все файлы репозитория» — `personal_search` ненадёжен для этой цели (см. риски #2, #3). Единственный способ получить гарантированно полный список — попросить пользователя проверить через сам GitHub (веб-интерфейс или `git clone` + `find`). Не полагаться на реконструкцию списка файлов через серию поисковых запросов как на исчерпывающую — это даёт «лучшее из доступного», не гарантию полноты.

`docs/lpf-reglament-v2.5.md` больше не единый файл — разбит на 9 частей + оглавление в `docs/reglament/` (см. правило 4, уточнение 2). Старый путь оставлен редиректом (не удалён), но любая ссылка вида «см. `docs/lpf-reglament-v2.5.md`, раздел N» или «см. `LPF-reglament.md`» — устарела и должна вести на конкретную часть в `docs/reglament/` (нумерация частей — см. `docs/reglament/00-index.md`). При правке любого файла, где встречается такая ссылка — обновлять сразу, не откладывать. Найденные и исправленные 29.08.2026: `README.md`, `automation/repo-map.md`, `docs/otnosheniya-pravila.md`, `prompts/dnevnik-prompt.md`, `docs/drr-candidates.md`.

## 9. Gate для аналитики и выводов (с 31.08.2026)

Отдельно от рисков #2–4 выше (те про ТЕХНИКУ записи — свежесть чтения, гонки записи) — это правило про то, ЧТО можно записывать без явного разрешения. Перед `personal_write` любого файла, содержащего анализ, выводы, резюме или интерпретацию агента (не факт и не чистовой ответ, продиктованный пользователем дословно) — обязательно показать черновик в чате и записать только после явного «да»/«принято» от Марии. Это отдельный от Trust & Gates слой LPF-регламента (часть 2), но применяется и здесь как техническое правило репозитория, потому что ветка, которая никогда не читала регламент (см. ниже), всё равно обязана его соблюдать.

**Обнаруженная причина нарушения (31.08.2026):** инструкция для ветки «Треки обучения» в README не отправляет читать LPF-регламент вообще (только README + сводную заметку трека) — в отличие от Хаба (весь регламент) и проектных чаток (часть 9). Gate при этом входит в регламент (часть 2), а не в этот файл. Ветка «Обучение» технически не обязана была знать о Gate из собственной инструкции по чтению, хотя правило на неё явно распространяется. Нарушение: агент «Обучение» записал `raspozharizaciya/log.md` (аналитический журнал хода рассуждений трека) без Gate — обнаружено Марией постфактум, содержимое подтверждено уже после факта записи.

**Правило:** (1) перед записью аналитики/выводов — черновик в чат, ждать «да»/«принято», как описано выше; (2) в README, в инструкции для каждой ветки, которая не читает весь LPF-регламент, должна быть явная отсылка на Gate — не полагаться на то, что правило «само собой» дойдёт из общего регламента, если ветка его не читает.

## 10. Единый формат телеметрии в дневнике (с 05.09.2026)

Данные сна/энергии в `telemetry/diary-2026-XX.md` всегда записывать в формате `**Сон:** ...` / `**Энергия:** ...` (как в большинстве дней), не текстом в свободном абзаце — даже если запись делается на бегу или задним числом.

**Причина:** недельная сводка (`docs/nedelnye-svodki.md`, механика — регламент часть 7) ищет данные именно по этому формату; отклонение от него (как в записи 01.09.2026, где сон/энергия были даны текстом внутри абзаца) даёт ложный «Missing» в сводке, хотя данные на самом деле есть — просто не в искомом формате. Обнаружено и разобрано 05.09.2026 (см. поправку в `docs/nedelnye-svodki.md` от того же дня).

**Правило:** решение проблемы — не менять формат под конкретный случай постфактум, а всегда соблюдать единый формат при записи, независимо от обстоятельств записи (в моменте, вечером, задним числом).

## 11. Контент в файле не совпадает ни с одной успешной записью агента (с 08.09.2026) — не подтверждено, требует эскалации в техподдержку

Отдельно от рисков #3/#4 (стейл-рид, гонка записи между ветками) — здесь зафиксирован случай, когда сам факт гонки не объясняет наблюдаемое. Хронология на файле `telemetry/diary-2026-09.md`:

1. `personal_get_document(include_sha=true)` → sha `A`, запись за конкретную дату в файле отсутствует.
2. Агент формирует и отправляет `personal_write` с собственным текстом этой записи, `expected_sha=A`.
3. Запись **отклонена** инструментом: `{"success": false, "reason": "version_mismatch", "current_sha": "B"}` — то есть контент агента точно не попал в файл.
4. Немедленный повторный `personal_get_document(include_sha=true)` → sha `B` (совпадает с `current_sha` из отказа), и в файле уже стоит запись за ту же дату — но с **другой формулировкой**, не совпадающей с текстом агента из шага 2.
5. Пользователь подтвердил, что не вносил эту запись сам ни в этом чате, ни (по её словам) в параллельной сессии.

**Чем это отличается от уже описанных рисков:** #3 объясняет, что чужая ветка могла успеть записать раньше — это нормально и ожидаемо. Но здесь нет кандидата на «чужую ветку» (пользователь отрицает параллельную сессию), а главное — формулировка нового контента текстуально не совпадает с отклонённой попыткой самого агента, то есть это не «частичное просачивание» неудавшейся записи агента.

**Не установлено (решить с техподдержкой AIAssystant/MCP):**
- Есть ли фоновый процесс, способный писать в личный репозиторий без явного вызова `personal_write` в текущей сессии (агрегатор телеметрии, кэш-подстановка и т.п.)?
- Не является ли это фантомной выдачей на чтение (шаг 4 отдаёт контент, которого нет в реальном git-состоянии), а не реальной записью?
- Возможна ли сверка через git-историю коммитов файла на стороне GitHub App, привязанного к MCP-подключению?

**Правило до выяснения:** после любого `version_mismatch` — не считать, что «кто-то из своих подхватил» по умолчанию. Явно спросить пользователя, вела ли она параллельную сессию; если нет — не списывать на риск #3, фиксировать как неопознанный инцидент по этому пункту и не заносить дальнейшие правки в файл без повторной сверки содержимого построчно.

## ПРОЦЕДУРА: Проверка целостности системы (с 29.08.2026)

Запускается после любой структурной операции: разбиение файла на части, массовое переименование, перенос источника истины (например, из Google Docs в репо или наоборот), любая правка, затрагивающая больше одного файла разом.

1. **Реиндекс.** `personal_reindex_source` → дождаться `succeeded`. Зафиксировать итоговое число файлов и сверить с ожидаемым (было N, стало N + добавленные − удалённые).
2. **Существование файлов.** По каждому файлу, упомянутому в README, — подтвердить, что он реально существует (`personal_get_document` или `personal_search` по точному пути), не полагаясь на память о том, что «должно быть».
3. **Битые ссылки.** По каждой перекрёстной ссылке в изменённых файлах (например, «см. раздел 8» после разбиения на части) — убедиться, что она указывает на реально существующий путь или раздел, а не в никуда.
4. **Смысловая полнота ключевого файла.** Для главного изменённого документа — явный контрольный список того, что должно остаться (например, для регламента: все 14 Ситуаций по номерам, все разделы по старой нумерации), сверка поштучно, не «пробежала глазами».
5. **Промпты веток — путь и ссылки целы.** Для каждой ветки со своим промптом (сейчас: Дневник) — открыть промпт-файл и пройти по каждой ссылке/пути, на который он ссылается (LPF-регламент, otnosheniya-pravila.md, o-marii-fakty-lyudi.md, neudovletvorennosti.md, лексикон и т.д.): путь существует, ведёт туда, куда написано, не на устаревший или переименованный файл. Отдельно проверить раздел START OF DAY/чтения при старте — именно там чаще всего накапливаются ссылки на несколько файлов, и именно там разрыв незаметен до тех пор, пока ветка не перезапустится с нуля.
6. **Контрольное чтение с чистого листа.** Пройти инструкцию из README так, как если бы это делал новый агент при первом запуске (реально прочитать файлы по цепочке, а не по памяти о том, что там должно быть) — путь не должен обрываться и не должен вести в никуда.
7. **Сравнение со снапшотом (если он есть для этой операции).** Например, для разбиения регламента — сверить, что каждый раздел архивного снапшота (`docs/archive/lpf-reglament-v2.6-snapshot-2026-08-29.md`) нашёл своё место в новой структуре: ничего не потеряно, ничего не задвоено.

**Правило:** процедура прогоняется целиком, не выборочно — пропуск одного пункта («это же мелкая правка») ровно то, из-за чего произошёл инцидент #6 выше.

## ПРОЦЕДУРА: Полный бэкап IWE (с 29.08.2026)

Бэкап всего репозитория целиком, вне репозитория — на случай потери самого репо (не спасают снапшоты отдельных файлов внутри него самого).

**Периодичность:** раз в неделю, привязано к ритуалу недельной сводки (см. `docs/reglament/07-propuski-svodka.md`) — та же сессия, заодно; плюс дополнительно перед любой крупной структурной операцией (например, перед разбиением регламента 29.08.2026).

**Способ (обновлено 29.08.2026 — предпочтительный метод сменился по опыту первого бэкапа):** основной способ — пользователь скачивает репозиторий целиком через GitHub («Code» → «Download ZIP») и сохраняет архив сам (например, в Google Drive вручную). Это даёт гарантированно полную и точную копию без риска пропусков, в отличие от попытки агента реконструировать содержимое через `personal_search`/`personal_get_document` (см. риск #7 — эти инструменты не гарантируют полноты списка файлов, и на больших файлах режут содержимое, см. риск #4, уточнение 2).

Агент может дополнительно собрать вспомогательный документ (список файлов, структура, найденные через поиск фрагменты) и сохранить в Google Drive как **дополнение**, явно помеченное «не гарантированно полная копия» — но не как замену ZIP-архиву пользователя.

**Хранение:** пользователь держит несколько последних ZIP-архивов с датой в названии (например, «DS-maria-lpf — 29.08.2026.zip»). Явного лимита нет — это делает пользователь у себя, не агент.

## ПРОЦЕДУРА: Восстановление из бэкапа (с 29.08.2026)

**ZIP-архив восстанавливает содержимое файлов на 100% — но не всю архитектуру целиком.** Четыре вещи находятся за пределами архива и требуют отдельных шагов после распаковки:

1. **История коммитов (git-история) не входит в ZIP.** ZIP — это срез файлов на момент времени, не хронология правок. Если репозиторий пересоздаётся из ZIP с нуля (не восстанавливается тот же самый) — история «кто/когда/зачем менял» (сообщения коммитов, sha) теряется безвозвратно. Содержимое файлов цело, история правок — нет. Если возможно физически (репозиторий не уничтожен, а только повреждён/испорчен) — предпочтительнее откатить нужные файлы через git (например, вернуть предыдущий коммит), а не пересоздавать репозиторий с нуля из ZIP, именно чтобы сохранить историю.

2. **Подключение к Aisystant (MCP) нужно переустановить, если репозиторий пересоздан заново.** Новый (не тот же) репозиторий потребует: `personal_connect_source` → дождаться подключения → `personal_reindex_source` → дождаться `succeeded`. Это не потеря данных, а обязательный технический шаг, который легко забыть в стрессовой ситуации восстановления.

3. **Внешние источники в Google Docs не защищены ни ZIP, ни этим бэкапом.** Несколько файлов до сих пор ссылаются на исходники вне репозитория (журнал изменений, журнал отношений, сводные заметки по трекам обучения и другие — см. README). Если инцидент коснётся конкретно репозитория — они не пострадают. Но если проблема на уровне Google-аккаунта — ни ZIP, ни репозиторий их не спасают. Это отдельный риск, не покрытый текущей процедурой бэкапа.

4. **Состояние Telegram-бота с напоминаниями не восстанавливается автоматически.** `automation/reminders-routine.md` описывает конфигурацию слотов и правило продления, но уже запущенные напоминания (последний известный батч: 28.08–03.09.2026) — это состояние самого бота (@aist_me_bot). Восстановление файла из бэкапа не восстанавливает автоматически ранее поставленные напоминания — после любого восстановления нужно явно попросить агента «продлить напоминалки» заново по инструкции из файла.

**Правило:** после каждого крупного бэкапа — рекомендуется тестовое восстановление (не дожидаясь реальной катастрофы): взять актуальный ZIP, попробовать реально пройти шаги 1-4 выше в тестовом виде хотя бы раз, чтобы процедура была проверена на практике, а не оставалась предположением «наверное, сработает».

- **[28.08.2026] Общее правило для всех веток: при создании нового файла — README должен обновляться в той же операции.** Сейчас README регулярно расходится с фактической структурой репо, потому что обновление README не было обязательным шагом при создании файла.
