# IWE совершенствование — журнал рассуждений

Ветка мета-уровня: работа над самой архитектурой IWE-системы (структура репо, роли файлов, правила агентов) — не про Марию как человека (это LPF-регламент), не про конкретный проект, а про инструмент, которым Мария и агенты пользуются.

Формат записи — «рабочая запись» по FPF (см. `FPF_подход_левенчук` в Google Drive, раздел 7): Entity of Concern / Bounded Context / Текущее утверждение / Intended Use / Основание. Цель — чтобы другой агент мог продолжить рассуждение по записи без устного восстановления (FPF, «коллективное мышление возникает, когда...»).

## Запись 1 — Разделение трёх слоёв документации репо

**Дата:** 28.08.2026
**Entity of Concern:** структура репозитория `DS-maria-lpf`, конкретно — куда класть новое правило, когда оно появляется.

**Bounded Context:** чат «Дневник», 28.08.2026, после того как в `automation/repo-map.md` было ad-hoc добавлено операционное правило про телеметрию.

**Текущее утверждение (Claim):** в репозитории должны существовать три независимых, несмешиваемых слоя документации:

1. **Промпт/тон ветки** («кто я и как говорю») — по одному документу на роль чата (Хаб, Дневник, проектные чаты, треки обучения), живёт как ссылка в README → раздел «Инструкции для веток».
2. **LPF-регламент** (`docs/lpf-reglament-v2.5.md`) — «как думать про Марию»: психологические паттерны, именованные Ситуации (0, 5, 8...), правила несмешивания ролей. Меняется только через явный цикл DRR (раздел 16 регламента), не ad-hoc.
3. **`automation/agent-workflow-rules.md`** — «как технически вести файлы репо»: дисциплина записи, не психология и не тон. Растёт по одному пункту за раз, с датой, без переписывания старых пунктов.

`automation/repo-map.md` — отдельно от всех трёх слоёв, это чистый манифест структуры («что где лежит»), без единого правила поведения внутри.

**Intended Use:** любой агент (человеческий или ИИ), который собирается добавить новое правило/инструкцию в этот репо, сначала должен определить — к какому из трёх слоёв оно относится — и положить туда. Если непонятно, к какому слою относится правило — это сигнал остановиться и спросить, а не класть в repo-map «на всякий случай» (repo-map не резиновый).

**Основание (Evidence):** инцидент этого же дня — правило «утреннюю телеметрию писать в файл сразу, не откладывая до вечера» было первым заходом положено прямо в `repo-map.md`. Пользователь указала на риск: если так продолжать, там скоро будет несколько сотен правил и манифест станет нечитаемым. Правило перенесено в новый файл `automation/agent-workflow-rules.md`, `repo-map.md` возвращён к чистой структуре. Различие «слой 1 (промпт ветки) vs слой 3 (workflow-rules)» уточнено отдельно: `agent-workflow-rules.md` — общий для всех веток технический слой, а не персона конкретной ветки.

**Reopen Condition:** если через несколько недель `agent-workflow-rules.md` тоже разрастётся до состояния «нечитаемо» — разбить по подпапкам (`automation/workflow/<тема>.md`) вместо продолжения линейного списка.

## Запись 2 — Запрос на единого «главного» ассистента поверх текущей архитектуры веток

**Дата:** 12.09.2026

**Entity of Concern:** архитектура IWE-системы — множество независимых веток (Хаб, Дневник, проектные чаты, треки обучения), каждая со своим промптом и жёстким правилом несмешивания тем.

**Bounded Context:** чат «Дневник», 12.09.2026 (суббота), после повторного раздражения правилом несмешивания (хронометраж — тема Хаба, эмоция от хронометража — тема Дневника, хотелось обсудить в одном месте).

**Текущее утверждение (Claim, со слов Марии):** хочет одного главного ассистента, который сам «раскладывает по полочкам» остальным — единая точка входа вместо необходимости самой помнить и переключаться, какая ветка за что отвечает.

**Статус: открытый вопрос, не решение.** Не запускать реструктуризацию с ходу — есть два принципиально разных варианта, которые пока не разведены:
(а) диспетчер/оркестратор поверх существующих специализированных веток (одна точка входа, сама маршрутизирует, специализация внутри сохраняется);
(б) полный отказ от разделения по темам в одном ассистенте.
Вариант (б) — это откат к состоянию до 28-29.08.2026, когда смешение статусов и эмоций уже давало кашу (см. Запись 1). Вариант (а), вероятно, решает именно ту боль, что всплыла сегодня, без этого риска.

**Intended Use:** при следующем разборе архитектуры (сессия Стратега или отдельно здесь, в IWE) — сначала явно развести (а) и (б) с Марией, прежде чем менять что-либо.

**Основание (Evidence):** инцидент 28-29.08.2026 (смешение эмоций/статусов, см. Запись 1) произошёл в работе с Qwen, не с Claude — сама архитектура репозитория и разделение веток спроектированы независимо от конкретной модели-исполнителя. Повторное раздражение правилом несмешивания сегодня, 12.09 (тема хронометража), уже в работе с Claude. Прямая формулировка Марии выше.

**Третий эпизод (12.09.2026, тот же день):** конкретный механический пробел, не только «хочется одного окна». Время, проведённое в чате «Дневник» на нерабочие темы, не попадает в хронометраж автоматически — учёт идёт только пока открыта сессия Хаба. Пример: сессия «Дневник» сегодня заняла ощутимое время, часть — предметный разговор (страх/деньги, IWE-архитектура), но в хронометраже это никак не отразится, если не пересказать вручную вечером. Указывает конкретно на вариант (а) из этой записи — диспетчер/мост между ветками для учёта времени, а не отказ от разделения как такового.

**Reopen Condition:** снять статус «открытый вопрос» после явного разбора (а)/(б) с Марией.

## Запись 3 — Развод (а)/(б): специализация остаётся, чинится надёжность фоновых механизмов

**Дата:** 13.09.2026

**Entity of Concern:** та же архитектура, что в Записи 2 — развилка «диспетчер поверх веток» (а) vs «один ассистент на всё» (б).

**Bounded Context:** чат «Дневник», 13.09.2026 (воскресенье), длинная сессия — недельный разбор продуктивности, DRR (4 гейта за сессию), Стратег (видение сформулировано впервые), затем прямой запрос Марии разобрать вопрос диспетчера из Записи 2.

**Текущее утверждение (Claim):** (а) и (б) разведены явно. Выбор — **не (б)**: полное слияние веток не нужно, Хаб как «хранитель фокуса» ценен сам по себе (прямые слова Марии: «если смешать дневник и хаб — будет ни то ни сё»). Выбор — **модифицированный (а), но не в форме отдельного диспетчер-агента**, а в форме конкретных исправлений надёжности существующих механизмов:

1. **Разделение веток и техническая изоляция инструментов — разные вещи.** Сегодняшняя сессия сама была живым доказательством: агент «Дневник» весь день свободно читал и писал в файлы Хаба (портянка, хронометраж, регламент) без единого технического препятствия. Граница Хаб/Дневник — это управленческая договорённость про тон и фокус разговора, не технический барьер доступа к данным. Комбинированные сессии (как сегодня, или уже существующий прецедент — Коуч в том же чате, что Хаб+Дневник) остаются возможными как **исключение для плотных content-сессий**, не становятся нормой для будничного рабочего темпа.

2. **Найдена и исправлена настоящая причина «потери ценности между ветками»** (пункт 1 из недовольств Марии на сегодняшней сессии: «за счёт разделения я теряю IWE как ценность»). Дело не в отсутствии диспетчера, а в том, что механизм переноса знания между ветками (роль «Экстрактор», роутинг в Pack) был **дырявым с обеих сторон**:
   - **Сторона записи:** существовал только как фоновая инструкция «замечай сама по ходу» — систематически не срабатывала. Проверка: за месяц ни один из трёх активных проектных чатов (ПИШ, Химозин, общий ЦПИ+УСС) не дал ни одной записи в Pack, хотя работа там точно шла. Тот же класс отказа уже был зафиксирован 05.09.2026 для PEOPLE INTAKE (см. `docs/drr-candidates.md`).
   - **Сторона чтения (обнаружена позже в той же сессии):** даже там, где Pack пополняется (курс обучения, разбор Тандема), ни один проектный промпт не читал Pack на старте сессии вообще. Новый проектный чат по тому же самому проекту оставался «таким же глупым», как первый, несмотря на накопленные находки — прямая формулировка Марии.

**Решение, реализованное в тот же день:**
- `automation/session-close-routing.md` переработан: явные триггерные фразы закрытия сессии («стоп на сегодня» и т.п.) вместо неявного «при закрытии сессии»; чек-лист расширен с 3 вопросов до 5 активных блоков с готовыми черновиками (включая доменное знание и метод работы — раньше это была фоновая часть Экстрактора, теперь явный блок ритуала); Gate по каждому блоку отдельно.
- `prompts/project-branch-prompt.md` синхронизирован дважды за сессию: (1) чтение части 5 регламента (Ситуации) добавлено в старт сессии — раньше проектные чаты не узнавали личные паттерны Марии в рабочем разговоре вообще; указатель на новый ритуал закрытия вместо старого пассивного описания Экстрактора; (2) чтение Pack на старте сессии — всегда `pack/operacionnyj-menedzhment.md`, плюс релевантные доменные файлы по описанию из README.
- `automation/role-trials.md`: пилот Экстрактора переработан (новый механизм — пишет и теперь читается, новая дата сверки), добавлен общий системный урок про ненадёжность фоновых «замечай сама» инструкций.

**Intended Use:** это закрывает Запись 2 как решённую практически (обе стороны цикла знания — запись и чтение — теперь явные, не фоновые), но открывает частный вопрос ниже (см. Reopen Condition) — сама техника «явный триггер вместо фоновой инструкции» скорее всего понадобится ещё не раз при проектировании новых механизмов (см. также пункт про `otnosheniya-pravila.md` в разделе «Планируется» ниже — та же болезнь), стоит держать в уме как общий принцип, а не разовую заплатку.

**Основание (Evidence):** прямая формулировка Марии по пункту 2 Хаба («хаб сохраняет мне фокус»), по пункту 1 недовольств («я теряю IWE как ценность») и по вопросу о чтении Pack («он снова будет такой же глупый») — все три цитаты с сессии 13.09.2026. Технический факт — пустой `pack/` от трёх реальных проектных чатов при формально существующем правиле роутинга, обнаружен в этой же сессии прямой проверкой.

**Reopen Condition:** если после недели-полутора работы нового ритуала закрытия и чтения Pack (см. дату сверки Экстрактора в `role-trials.md`, 20-27.09.2026) находки по-прежнему не появляются в Pack из обычных рабочих сессий, или появляются, но не влияют на качество работы в новых сессиях того же проекта — значит, проблема не только в отсутствии явных триггеров, а в чём-то ещё (например, сами триггерные фразы Марии произносятся редко, или патчи physически не разнесены по существующим Custom Instructions) — тогда стоит вернуться к варианту (а1) полноценного диспетчера или другому механизму.

**Промежуточная сверка (20.09.2026, из ветки IWE_Церен):** проверены `pack/`-файлы трёх контрольных проектов из этой записи. Результат частичный: `pack/pish.md` (дата сверки 19.09.2026) и `pack/startup-studio.md` (дата сверки 16.09.2026) — обе записи свежие, обновлены именно на этой неделе. По Химозину файла в `pack/` по-прежнему нет; проверено отдельно (тот же день) — активной рабочей сессии по Химозину за 14–20.09 не было. Черновик представлен Марии в чате, подтверждён явным «да» 20.09.2026 (Gate соблюдён).

**Итог сверки:** механизм записи в Pack работает как минимум для 2 из 3 контрольных веток на реальных находках этой недели. Пустой `pack/himozin.md` объясняется отсутствием сессий, а не отказом триггера — не засчитывается как провал. Reopen Condition в исходной формулировке (полный провал по всем трём веткам) **не наступил** — статус записи закрыт практически. Следующая проверка — не по календарю, а по факту: при первой активной рабочей сессии по Химозину после 20.09.2026 посмотреть, появится ли `pack/himozin.md` — если сессия пройдёт, а Pack снова останется пустым, это и будет первый настоящий сигнал отказа механизма для конкретно этой ветки.

**Сверка 27.09.2026 (IWE_Церен):** со слов Марии — Pack пишется, механизм работает. Хвост по Химозину снят. Запись закрыта.

## Запись 4 — Рабочий продукт (РП) как явная единица сессии, с реестром

**Дата:** 13.09.2026

**Entity of Concern:** единица работы в проектных/учебных ветках LPF — сейчас это «проект» (папка `<slug>/context.md`) и запись в общей портянке, без промежуточного слоя «что за артефакт должен появиться из этой конкретной сессии».

**Bounded Context:** ветка «IWE_Церен», разбор транскрипта эфира Мастерской IWE (Церен Церенов, гость Лари) от 12.09.2026 — обсуждение конвейера Лари в системе на VS Code + Claude Code CLI (MIM), не LPF. Материал сохранён в `obuchenie/tseren/2026-09-12-intellektualnaya-sreda-i-put-zumera.md`.

**Текущее утверждение (Claim):** идея «рабочий продукт (РП) как единица сессии + реестр РП с номером/названием» переносима в LPF без переезда на кодовую механику MIM. `claude/comparison-mim-vs-lpf.md` (05.09.2026) отбросил весь WP-слой MIM как «кодовую механику, нужную только для дисциплины агентов в терминале» (executor-catalog, Gate-скрипты, git-хуки). Разбор транскрипта показывает, что вывод был верен только для скриптовой обвязки WP, не для самой идеи единицы работы: у Лари РП-дисциплина (сессия = РП, РП регистрируется под номером и названием) держится в чат-режиме, без Claude Code и без скриптов.

**Практическая польза для LPF:** сейчас портянка фиксирует задачи, а не артефакты сессии; нет вопроса «к какому результату должна прийти именно эта сессия», нет реестра завершённых/незавершённых РП по номерам. Прямая связь с открытым остатком Записи 2/3 этого же лога — учёт времени между ветками: РП как единица даёт естественную точку учёта («эта сессия = РП №N»), не только категорийный хронометраж.

**Intended Use:** при следующем touch тайм-трекинга или портянки — рассмотреть добавление слоя «РП сессии» (номер, название, статус) поверх существующей структуры, не заменяя её и не создавая отдельно от портянки. Проверить сначала на одном проекте (кандидат — ПИШ или Химозин, наиболее активные), прежде чем распространять на все ветки.

**Основание (Evidence):** пересказ (не дословная цитата) слов Лари из транскрипта — переход от 20–30 параллельных незавершённых сессий к регистру РП с номером/названием ускорил доведение работы до результата. Черновик разбора представлен Марии в чате, подтверждён явным «да» 13.09.2026 (Gate соблюдён).

**Reopen Condition:** если после пробного внедрения на одном проекте РП-слой окажется дублирующим портянку без дополнительной пользы (просто ещё один список задач под другим именем) — отказаться, не встраивать во все ветки.

**Внедрено 27.09.2026 (сверка в IWE_Церен, со слов Марии):** не пилотом на одном проекте, а сразу во всех проектных ветках — через `prompts/project-branch-prompt.md`, раздел «СЛОТ: открытие и закрытие». Любая работа начинается с открытия слота: понимание задачи, РП (существительное, не глагол), цель; исполнение — только после подтверждения Марии. **Реестр РП не заводится** (решение Марии) — вместо него на закрытии сессии проверка: все ли слоты закрыты и заявленные РП реально записаны туда, куда обещано. Новый Reopen Condition: если на закрытии регулярно всплывают незакрытые РП без решения «получилось/не получилось/отложили» — проверки на закрытии недостаточно, вернуться к вопросу о реестре.

## Запись 5 — Явный конвейер «вход → действие → выход» для повторяющихся процессов

**Дата:** 13.09.2026

**Entity of Concern:** повторяющиеся многошаговые процессы Марии, которые сейчас существуют как шаблоны выхода (готовый формат результата), но не как формализованная последовательность этапов со входами/выходами на каждом.

**Текущее утверждение (Claim):** минимум три существующих в LPF процесса — справка «6 осей» для СД (`prompts/spravka-6-osey-shablon.md`), постмортем мероприятия (пример: `katalist/2026-09-01-postmortem-picnik.md`), скрининг проекта-кандидата для стартап-студии (материалы Технопрома, `docs/tehnoprom-2026-materialy.md`) — уже имеют формализованный **выход** (шаблон/структуру результата), но не формализованные **вход** и **действие** по этапам. ## Запись 6 — README как узкое место каталога: разгрузка в repo-map.md

**Дата:** 13.09.2026

**Entity of Concern:** README.md как единственный файл, через который обязана пройти запись при появлении любого нового файла в репозитории (правило 6/кандидат от 28.08.2026) — при семантике `personal_write` «только полная перезапись, без append/patch» (см. `automation/agent-workflow-rules.md`, правило #6, уточнение 13.09.2026) это создаёт две проблемы: (а) стоимость каждой правки растёт пропорционально размеру всего README, а не размеру самой правки; (б) README — единая точка гонки записи между параллельными ветками (уже наблюдалась 28-29.08.2026).

**Bounded Context:** ветка «IWE_Церен», прямая жалоба Марии 13.09.2026 («файл ридми — очень долго пишется, я поняла что у меня в репо будет множество файлов») в процессе третьей подряд правки README за один день.

**Текущее утверждение (Claim):** принят кандидат от 13.09.2026 из `automation/agent-workflow-rules.md` → «Кандидаты» (части 1 и 2; часть 3 оставлена отдельным открытым пунктом для DRR, не архитектурная). Решение — двухуровневое обновление каталога, GATE как правило 13 в `automation/agent-workflow-rules.md`:
1. README хранит только домены верхнего уровня (ветки, роли, проекты, топ-папки) — одна строка на домен.
2. Построчный каталог файлов внутри домена — целиком в `automation/repo-map.md`, ранее задуманном для этой роли (см. Запись 1), но фактически не использовавшемся по назначению — актуальная картина держалась в README, оба файла дублировали друг друга.
3. Обновление README требуется только когда рождается новый домен (новый проект/ветка/топ-папка) — то же событие, что и раньше. Обновление `repo-map.md` для обычного нового файла внутри существующего домена — не обязательно в ту же сессию, разбор пачкой раз в неделю на Хабе вместе с недельной сводкой.

**Intended Use:** любой агент, создающий файл внутри уже существующего проекта/папки, добавляет ссылку в `repo-map.md`, не в README. README трогают только при появлении нового домена целиком.

**Основание (Evidence):** технически подтверждено 13.09.2026 — схема инструмента `personal_write` не содержит параметра append/diff, только `content` (полный текст) + `expected_sha` (проверено вызовом `tool_search`). `repo-map.md` был на момент решения заметно отставшим от README (не хватало `pish/`, `katalist/`, большей части `startup-studio/`, файлов Тандема и Хелснета) — досинхронизирован в рамках этой же операции. По ходу выполнения план столкнулся с гонкой записи вживую: параллельная ветка/сессия успела записать `repo-map.md` раньше (получен `version_mismatch`, см. правило #3 в `automation/agent-workflow-rules.md`) — механизм `expected_sha` сработал как описано, конфликт обнаружен и разрешён слиянием, не потерей данных.

**Reopen Condition:** если через 2-3 недели `repo-map.md` снова заметно отстанет от факта (недельная сверка не удерживает синхронность) — вернуть синхронность «в ту же сессию» для repo-map (но не для README), либо искать другой механизм пакетной синхронизации.

**27.09.2026:** срок проверки по Reopen Condition наступил (2 недели). Сверка `repo-map.md` с фактическим содержимым репо — не проведена, следующий шаг в IWE_Церен.
