# IWE совершенствование — журнал рассуждений

Ветка мета-уровня: работа над самой архитектурой IWE-системы (структура репо, роли файлов, правила агентов) — не про Марию как человека (это LPF-регламент), не про конкретный проект, а про инструмент, которым Мария и агенты пользуются. Ведёт — ветка IWE_Церен (мета-ветка IWE с 27.09.2026, отдельного чата «IWE совершенствование» нет).

Формат записи — «рабочая запись» по FPF (см. `FPF_подход_левенчук` в Google Drive, раздел 7): Entity of Concern / Bounded Context / Текущее утверждение / Intended Use / Основание. Цель — чтобы другой агент мог продолжить рассуждение по записи без устного восстановления (FPF, «коллективное мышление возникает, когда...»).

**Как вести этот файл (с 27.09.2026, Запись 9):** здесь — только открытые записи и короткая очередь. Закрытая запись уезжает дословно в архив месяца (`iwe-development/arhiv-log-<ГГГГ-ММ>.md`, пишется один раз), здесь от неё остаётся строка в индексе. Нумерация сквозная, номера не переиспользуются. Пункт «Планируется» — 2–3 строки; подробности появляются в записи, когда задача взята в работу.

## Запись 4 — Рабочий продукт (РП) как явная единица сессии, с реестром

**Дата:** 13.09.2026

**Entity of Concern:** единица работы в проектных/учебных ветках LPF — сейчас это «проект» (папка `<slug>/context.md`) и запись в общей портянке, без промежуточного слоя «что за артефакт должен появиться из этой конкретной сессии».

**Bounded Context:** ветка «IWE_Церен», разбор транскрипта эфира Мастерской IWE (Церен Церенов, гость Лари) от 12.09.2026 — обсуждение конвейера Лари в системе на VS Code + Claude Code CLI (MIM), не LPF. Материал сохранён в `obuchenie/tseren/2026-09-12-intellektualnaya-sreda-i-put-zumera.md`.

**Текущее утверждение (Claim):** идея «рабочий продукт (РП) как единица сессии + реестр РП с номером/названием» переносима в LPF без переезда на кодовую механику MIM. `claude/comparison-mim-vs-lpf.md` (05.09.2026) отбросил весь WP-слой MIM как «кодовую механику, нужную только для дисциплины агентов в терминале» (executor-catalog, Gate-скрипты, git-хуки). Разбор транскрипта показывает, что вывод был верен только для скриптовой обвязки WP, не для самой идеи единицы работы: у Лари РП-дисциплина (сессия = РП, РП регистрируется под номером и названием) держится в чат-режиме, без Claude Code и без скриптов.

**Практическая польза для LPF:** сейчас портянка фиксирует задачи, а не артефакты сессии; нет вопроса «к какому результату должна прийти именно эта сессия», нет реестра завершённых/незавершённых РП по номерам. Прямая связь с открытым остатком Записи 2/3 этого же лога — учёт времени между ветками: РП как единица даёт естественную точку учёта («эта сессия = РП №N»), не только категорийный хронометраж.

**Intended Use:** при следующем touch тайм-трекинга или портянки — рассмотреть добавление слоя «РП сессии» (номер, название, статус) поверх существующей структуры, не заменяя её и не создавая отдельно от портянки. Проверить сначала на одном проекте (кандидат — ПИШ или Химозин, наиболее активные), прежде чем распространять на все ветки.

**Основание (Evidence):** пересказ (не дословная цитата) слов Лари из транскрипта — переход от 20–30 параллельных незавершённых сессий к регистру РП с номером/названием ускорил доведение работы до результата. Черновик разбора представлен Марии в чате, подтверждён явным «да» 13.09.2026 (Gate соблюдён).

**Reopen Condition:** если после пробного внедрения на одном проекте РП-слой окажется дублирующим портянку без дополнительной пользы (просто ещё один список задач под другим именем) — отказаться, не встраивать во все ветки.

**Внедрено 27.09.2026 (сверка в IWE_Церен, со слов Марии):** не пилотом на одном проекте, а сразу во всех проектных ветках — через `prompts/project-branch-prompt.md`, раздел «СЛОТ: открытие и закрытие». Любая работа начинается с открытия слота: понимание задачи, РП (существительное, не глагол), цель; исполнение — только после подтверждения Марии. **Реестр РП не заводится** (решение Марии) — вместо него на закрытии сессии проверка: все ли слоты закрыты и заявленные РП реально записаны туда, куда обещано. Новый Reopen Condition: если на закрытии регулярно всплывают незакрытые РП без решения «получилось/не получилось/отложили» — проверки на закрытии недостаточно, вернуться к вопросу о реестре.

## Запись 5 — Явный конвейер «вход → действие → выход» для повторяющихся процессов

**Дата:** 13.09.2026

**Entity of Concern:** повторяющиеся многошаговые процессы Марии, которые сейчас существуют как шаблоны выхода (готовый формат результата), но не как формализованная последовательность этапов со входами/выходами на каждом.

**Bounded Context:** та же ветка «IWE_Церен», тот же транскрипт (`obuchenie/tseren/2026-09-12-intellektualnaya-sreda-i-put-zumera.md`) — раздел 8, конвейер поиска работы Лари («вход → действие → выход» по этапам, плюс предложение Церена добавить нулевой этап — критерии отбора на входе).

**Текущее утверждение (Claim):** минимум три существующих в LPF процесса — справка «6 осей» для СД (`prompts/spravka-6-osey-shablon.md`), постмортем мероприятия (пример: `katalist/2026-09-01-postmortem-picnik.md`), скрининг проекта-кандидата для стартап-студии (материалы Технопрома, `docs/tehnoprom-2026-materialy.md`) — уже имеют формализованный **выход** (шаблон/структуру результата), но не формализованные **вход** и **действие** по этапам. Оформление их как явных конвейеров, а не только результирующих шаблонов, даёт две вещи: (а) видимость, на каком именно этапе застряла работа, а не только «результата ещё нет»; (б) материал для роли «Критик» (существует в LPF с 11.09.2026) — Критик сейчас применяется к готовым текстам, но по методу Церена может применяться и к устройству самого конвейера («попросить IWE критически проверить весь конвейер и предложить улучшения»).

**Intended Use:** не создавать сразу универсальный шаблон конвейера для всех трёх процессов. Начать с одного (кандидат — справка «6 осей», потому что для неё уже есть таблица соответствия шагов метода разделам справки в `prompts/spravka-6-osey-shablon.md`, то есть скелет входа/действия отчасти уже есть) и явно прогнать его через Критика на предмет устройства этапов, не только текста результата.

**Основание (Evidence):** транскрипт эфира Мастерской IWE, раздел 8 (конвейер поиска работы Лари, дополнение Церена про нулевой этап). Черновик разбора представлен Марии в чате, подтверждён явным «да» 13.09.2026 (Gate соблюдён).

**Reopen Condition:** если прогон одного процесса через явный вход-действие-выход не даст ничего сверх того, что уже есть в шаблоне результата — не распространять на остальные два.

**Уточнение Intended Use (27.09.2026, Gate Марии в IWE_Церен):** справка «6 осей» — слишком тяжёлый первый полигон; к 27.09 не начато. Тестировать конвейер сначала на лёгком повторяющемся процессе. Кандидат (гипотеза, не решение) — еженедельная сводка: алгоритм уже прописан (регламент, часть 7), входы известны (портянка, хронометраж, сводки веток), выход есть; не хватает только явных «вход → действие → выход» по этапам. Критерий пользы — видно, на каком шаге сводка застревает, а не просто «сводки нет». Справка «6 осей» — после, если полигон даст результат.

## Запись 9 — Цена поддержки IWE: вес живого файла × полная перезапись; сигнал «пора худеть»

**Дата:** 27.09.2026

**Entity of Concern:** стоимость поддержки самой системы — время и риск порчи данных при каждой правке служебных и проектных файлов.

**Bounded Context:** ветка IWE_Церен, 27.09.2026, после серии правок за день. Прямая формулировка Марии: «нельзя не дотачивать инструмент — иначе он начинает расползаться; каждую неделю это реально несколько часов работы».

**Текущее утверждение (Claim):**
1. **Главный драйвер часов — не думанье, а перетаскивание веса.** У `personal_write` нет режима «дописать» — каждая правка перепечатывает файл целиком. Цена правки = вес файла, не размер изменения. При этом живые служебные файлы росли append-only и не худели никогда.
2. **Замер по git-истории на 27.09.2026 (≈ КБ перепечатки в день = вес × правок в день):** `pish/context.md` 94 КБ × ~2/день ≈ 190; портянка 46 КБ × ~3/день ≈ 130; README 74 КБ × ~1,4/день ≈ 100; дневник (полумесячная часть) 49 КБ, растущий, × ~1,5/день ≈ 70–130; трекер Коуча 45 КБ × ~1/день. Плюс побочный эффект: большие файлы портятся при перезаписи (пример — `himozin/context.md` 27.09: вторая полная перепечатка 91 КБ только ради починки экранирования кавычек).
3. **Лечение — не «реже править», а держать живые файлы лёгкими:** живой файл содержит текущее состояние; прошедшее — в архивный файл (пишется один раз, больше не правится) или в git; длинные потоки режутся по периоду.
4. **Решение — сигнал, а не автоматическое худение.** Недельная сверка на Хабе (один вызов `personal_list_path`): живой файл ≥ 50 КБ — жёлтый флажок строкой в недельной сводке, ≥ 70 КБ — красный с предложением, как худеть. Решение — за Марией, по Gate. Статичные материалы (транскрипты, отчёты) не сигналят. Портянку не худеть без сигнала — похудела 24.09.

**Реализовано 27.09.2026 (Gate Марии):**
- `automation/repo-map.md` 50 → ~13 КБ (роль карты сменена, см. Запись 6); там же правило недельной сверки и порогов.
- `pish/context.md` 94 → ~27 КБ: текущее состояние + индекс моделей + люди; промежуточные разборы 20–26.09 — дословно в `pish/arhiv-context-2026-09.md`; в шапке правило «меняй текущее состояние, прошедшее — в архив».
- `README.md` 74 → ~20 КБ: одна строка на домен, без хроники; строка для Хаба про недельную сверку и сигнал. Блок активации Коуча перенесён в `prompts/coach-prompt.md`.
- Дневник — понедельная нарезка (Пн–Вс, файл не пересекает границу месяца): `diary-2026-09-16-20.md`, `diary-2026-09-21-27.md`, `diary-2026-09-28-30.md`; `diary-2026-09-16-30.md` — редирект. Правило имени и создания нового файла недели — в `automation/repo-map.md` → «Телеметрия» (Дневник туда и так смотрит), промпт Дневника менять не понадобилось.

- Итог: пять самых дорогих живых файлов облегчены примерно на 250 КБ на каждую следующую правку/чтение.

**Попутно зафиксировано (решение Марии):** хронометраж на паузе с 14.09.2026, не отменён — Мария вернётся к нему для нового замера. В README, карте и промпте Коуча помечено: пустые дни — не пропуски, ОРЗ по хронометражу пока «н/д».
