# Сравнение: FMT-exocortex-template (MIM) vs DS-maria-lpf (LPF v2.6)

Дата: 05.09.2026

## Вывод коротко

Полный переезд не имеет смысла — системы построены для разных сред исполнения. Есть смысл забрать 2-3 конкретных приёма, не трогая архитектуру LPF.

## Почему это разные системы, а не конкуренты

| | MIM (FMT-exocortex-template) | LPF (DS-maria-lpf) |
|---|---|---|
| Среда работы | VS Code + Claude Code CLI + терминал + bash-скрипты + git-хуки | Чат в Claude.ai Projects, без кода |
| Единица работы | WP (рабочий продукт) с Gate-проверкой, роутинг через executor-catalog.yaml | Проект/направление (`<slug>/context.md`), портянка задач |
| Роли | R1-R31: в основном разработческие (Кодировщик, Архитектор, Шаблонизатор, Верификатор) — заточены под цикл написания и ревью кода | Психологические/личные персоны (Жилетка, Друг с битой, Пледик, Подружка, Стратег) — заточены под рефлексию, эмоции, стратегирование |
| Протокол дня/сессии | ОРЗ реализован как скрипты (`day-open.sh`, `day-close.sh`) с блокирующими Gate и TodoWrite | ОРЗ существует неформально: утренний Хаб, вечерний чекин, хронометраж — работает через чат-инструкции, без скриптов |
| Хранение знаний | Pack — формализованная база домена как source-of-truth, отдельно от кода (DS) | Нет отдельного Pack; правила и знания живут в LPF-регламенте (9 частей) — но это регламент про Марию, не про предметную область (Хелснет, венчур и т.д.) |
| Разделение репозиториев | 5 семей (Base/PACK/DS/PD/MC) — нужно при масштабе с несколькими агентами и кодовой базой | Один репозиторий на всё (проекты + телеметрия + дневник + промпты) — осознанный выбор для «лёгкого» режима |

Итог: 90% содержимого MIM (scripts/, .claude/hooks, .githooks, executor-catalog, WP-Gate, роли R1/R6/R9/R23) существует ради дисциплины написания кода агентами в терминале. У LPF этой задачи нет и не будет, пока нет решения перейти на Claude Code — а такое решение прямо противоречит текущему «не буду кодить».

## Что можно позаимствовать точечно (без переезда)

1. **Явный Pack для предметного знания.** Сейчас у LPF есть `context.md` по каждому проекту (Хелснет, Тандем и т.д.) — это оперативный контекст, а не формализованная база знаний домена. Если со временем понадобится единый источник истины по здоровому-тех направлению (не «что происходит сейчас», а «как устроена область») — стоит завести отдельный файл/папку по образцу Pack, а не смешивать с context.md.

2. **Формализация ОРЗ как явного протокола с чек-листом.** У LPF ритуал открытия/закрытия дня уже есть де-факто (регламент часть 3), но не оформлен как отдельный проверяемый чек-лист наподобие `protocol-open.md`/`protocol-close.md`. Можно оформить как отдельный файл с явными пунктами «без этого не закрываем день» — не как скрипт, а как список для Хаба.

3. **Идея Gate уже есть и работает лучше, чем в MIM.** У LPF правило «аналитика/выводы — только после явного да» уже внедрено и соблюдается (README п.8, automation/agent-workflow-rules.md). В MIM это реализовано скриптами и веткой блокировок — LPF получает то же самое проще, через прямую инструкцию агенту. Тут заимствовать нечего, скорее наоборот.

## Что точно не подходит

- Вся кодовая механика: `.claude/hooks`, `.githooks`, executor-catalog, route-task.sh, TodoWrite-принудиловка — требует Claude Code CLI, которым ты не пользуешься.
- Роли R1-R31 — почти все или про код, или про операционку продукта (Триажёр, Публикатор, Синхронизатор для бота/контент-конвейера) — не про твою работу.
- 5 семей репозиториев — оверинжиниринг для одного человека с одним репозиторием; имеет смысл только если появится кодовая база или несколько независимых ИИ-агентов, которым нужна изоляция данных.

## Рекомендация

Оставить LPF как есть, взять пункт 1 (Pack для домена) и пункт 2 (явный чек-лист ОРЗ) как опциональные доработки — без переноса инфраструктуры MIM.
