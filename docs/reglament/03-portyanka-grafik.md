## 5. ПОРТЯНКА И ЖУРНАЛ ИЗМЕНЕНИЙ

**Портянка** — единый бэклог ВСЕХ незакрытых задач по ВСЕМ проектам.
- Файл: `docs/portyanka-obshiy-stek.md` в репозитории — **источник истины** (мигрировано из Google Docs; уточнено Марией 29.08.2026, что миграция уже завершена).

**Алгоритм работы с Портянкой:**
1. Структура: задачи группируются строго по проектам. Внутри каждого проекта два подраздела: «Активные» и «Выполнено».
2. Формат задачи: `[ ] 📅 дедлайн: ДД.ММ | 📌 создана: ДД.ММ: [Описание]`
3. УТРО: команда «обнови портянку» → агент читает `docs/portyanka-obshiy-stek.md` (форс-реиндекс перед чтением, если файл мог измениться в другой сессии — см. `automation/agent-workflow-rules.md`, правило 3).
4. ДЕНЬ: «добавь [проект] [задача]» / «закрой [проект] [задача]» → агент обновляет.
5. АГЕНТ-КОНТРОЛЬ: при обновлении агент вычисляет возраст задачи. Если с даты создания прошло >3 дней без прогресса, агент автоматически добавляет маркер `⚠️` и инициирует Ситуацию 5 (см. [часть «Ситуации»](05-situacii.md)).
6. ВЕЧЕР: агент выдаёт Candidate-блок → Мария проходит Gate → полная запись обратно в `docs/portyanka-obshiy-stek.md` через `personal_write` (полное содержимое файла, не только новый фрагмент — см. `automation/agent-workflow-rules.md`, правило 6).

**Журнал изменений** — теперь фиксирует только структурные сдвиги и недельные итоги, так как ежедневные открытия/закрытия задач видны прямо в разделах «Активные»/«Выполнено» внутри проектов.

Формат записи (по необходимости или в конце недели):
[Дата]
— Структурное: [Например: создан новый проект Х, изменена логика портянки]
— Итоги недели: [Проект] закрыто N задач, висит >3 дней: M задач.

## 6. РАБОЧИЙ ГРАФИК НА ДЕНЬ

Живёт в Хабе. Обновляется каждое утро.

[Дата] | Ёмкость: [низкая/средняя/высокая] | Статус: Candidate

**Приоритет формирования Candidate-графика:**
1. Задачи с `📅 дедлайн` на текущий день.
2. Задачи с маркером `⚠️` (висят >3 дней без хода, Ситуация 5).
3. Остальные задачи из бэклога — только при явном запросе Марии и наличии свободной ёмкости.

**Предиктивный флаг перегрузки:**

При построении графика агент сравнивает количество задач с ёмкостью:
- Обычный день: порог 5–7 задач
- День с тренировкой: порог 3–4 задачи

Если задач >порога, агент выставляет флаг: «⚠️ Риск перегрузки: N задач при ёмкости M. Что убираем или переносим?»

В Candidate-график при перегрузке автоматически включаются защитные элементы:

**Из [части «Ситуации»](05-situacii.md):**
- Слот обучения — через «поковыряние» (Ситуация 3), не пропускается молча
- Влетающая срочная → Ситуация 6 (лицензионный псих + микро-шаг)
- Если перегруз со вчерашним эмоциональным срывом + плохим сном → полный протокол Ситуации 7 («Утро после бури»)

**Обязательные слоты:**
- Принудительный перекус 17:00 — инвариант, не сдвигается (см. [часть 1](01-arhitektura-cikl.md))
- Обед сдвинут >30 мин → Ситуация 8: немедленная перехватка (белок/жиры, 15 мин)
- Тренировка отменена при перегрузе → замена на 15 мин растяжки/дыхания без вины (Ситуация 8)

**Из [части «System Constraints»](06-constraints-bridge.md):**
- Wind-down с 20:00, отбой 22:30 — без исключений

**Из [части «Ситуации»](05-situacii.md), Ситуация 9:**
- При тяге к алкоголю по приходу домой → чай с мёдом (часть ритуала «Выключение головы», см. [часть 1](01-arhitektura-cikl.md))

**Из `docs/otnosheniya-pravila.md`:**
- «Можно ли завтра?» — активнее к входящим
- Перед встречами — рекомендована калибровка (команда по запросу, см. [часть «Инструменты»](08-instrumenty.md))

График остаётся Candidate до Gate Марии. Без защитных слотов при перегрузке не предлагается.

## 7. ХРОНОМЕТРАЖ (добавлено 01.09.2026, курс «Распожаризация» R1.1:Tasks6)

**Цель:** увидеть разрыв между представлением о своей продуктивности и реальностью — по 6 категориям активности (Продуктивная / Инвестиционная / Лишняя / Активный отдых / Дом и быт / Минимальное ТО).

**Файл сырых данных:** `telemetry/hronometrazh-2026-XX.md` (по месяцу, аналогично `telemetry/history.md`).

**Роль Хаба — сбор в течение дня:**
1. При каждом обращении Марии в Хаб — проверить время последней зафиксированной записи в файле хронометража за сегодня.
2. Если есть разрыв с последней записью — коротко спросить: «Что делала с HH:MM до сейчас?» + категория (или предположить по смыслу сообщения, дать Марии подтвердить/поправить).
3. Если Мария сама пишет рабочую задачу — тайм-штамп самого сообщения уже даёт начало нового эпизода, отдельно спрашивать не нужно.
4. Вечером, на вечернем чекине — сверить записанные эпизоды с `docs/portyanka-obshiy-stek.md` (что реально закрывалось и когда), посчитать % по 6 категориям, пометить расхождения в столбце «Заметки» файла хронометража — не исправлять расхождения молча.

**Роль Дневника — вечерняя рефлексия (см. также `prompts/dnevnik-prompt.md`):** на вечернем чекине Дневник отдельным шагом читает файл хронометража за сегодня и содержание разговора с Марией в течение дня (эмоции, упомянутые активности) и предлагает дополнения/корректировки к записям Хаба — не переписывает файл сам, только предлагает, Мария подтверждает.

**Важно — гонка записи:** оба агента (Хаб и Дневник) пишут в один и тот же файл хронометража. Обязательно `personal_get_document(include_sha: true)` → `expected_sha` при каждой записи (см. `automation/agent-workflow-rules.md`, правило 3) — иначе вечерняя правка Дневника может затереть дневную сверку Хаба или наоборот.

**Осознанное отступление от методички курса:** методичка рекомендует опираться на реальные цифровые метки (тайм-штампы календаря/мессенджеров/трекера задач), а не на устный самоотчёт. Выбранная здесь схема (Мария сообщает Хабу в моменте + вечерняя сверка с портянкой) — компромисс в пользу низкого трения на захвате данных, при этом точнее, чем вспоминание в конце дня. Решение принято осознанно 01.09.2026 в ветке «Обучение» — не считать это методической ошибкой при следующих DRR-проходах.
