## НАБЛЮДЕНИЯ АГЕНТА (не из дневника)

Это не кандидаты с Evidence из твоего дневника — это выводы, которые я делаю по ходу работы с самой системой (репозиторием, инструментами, процессом). Статус тот же: ничего не действует без DRR и твоего Gate. Помечаю отдельно, чтобы не путать с дневниковыми паттернами.

- **Раздел 28.08 появился в этом файле без моего участия во время текущей сессии.** Я закрыла файл с 10 кандидатами, а при следующей проверке (после форс-переиндексации) в нём уже было 12 — добавлен раздел 28.08, судя по всему, другим инстансом/веткой (Хаб или Дневник), пока я работала здесь над восстановлением регламента. Кандидат в правило: если несколько веток одновременно пишут в один файл через `personal_write` (полная перезапись), есть риск гонки — одна ветка может затереть правки другой, если обе читают устаревший снимок и пишут поверх. Стоит явно решить: либо один файл = одна ветка-владелец, либо перед каждой записью в общий файл делать реиндекс + свежее чтение (как в этой сессии), а не полагаться на контекст предыдущего чтения.

- **Баг stale-read у `personal_get_document` не единичный случай, а системный риск для любого файла, не только для регламента.** В этой сессии я дважды была уверена, что вижу актуальный файл (10 кандидатов), пока форс-реиндекс + `personal_search` не показали 12. Без твоей прямой команды «проверь ещё раз» я бы дала неверный ответ. Кандидат в правило: для файлов, которые могут меняться из других веток (портянка, кандидаты, возможно дневник), правило «проверять полноту перед тем как считать факт установленным» (уже есть в agent-workflow-rules) стоит усилить конкретно — не просто `personal_search` по ключевым словам, а обязательный `personal_reindex_source` + `personal_search`/`get_document` после него, если файл мог быть тронут вне текущей сессии.

- **Публичная проверка через `web_fetch` на GitHub для приватного репозитория ненадёжна и может ввести в заблуждение.** Я один раз получила 404 на существующий (на тот момент) файл просто потому, что репозиторий приватный и анонимный fetch не имеет доступа — это выглядело как «файла нет», хотя файл был. Кандидат в правило: никогда не использовать анонимный `web_fetch` на GitHub-ссылки этого репозитория как способ подтвердить существование или содержимое файла — только `personal_*` инструменты.
